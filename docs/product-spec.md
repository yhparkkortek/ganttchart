### 왜 양식이 두 개인가
원본의 장 번호는 **손으로 고친 흔적**이 섞여 있다(Lower 의 `11.5 General TS Requirements`,
`12. Incoming Inspection Standard`, Topper 의 `12.2 Outline Dimension` 은 자동 번호가 아니라 글자다).
터치 장을 지웠다 넣었다 하면 번호가 어긋나므로, 원본 그대로인 두 판을 두고 `hasTouch`(YES/NO)로 고른다.

### 그림 칸
프로젝트 그림(전원 커넥터·블록도·A/D 보드·컨버터·OSD 키·OSD 메뉴·외형도·터치 보드·터치 도면)은
**회색 자리 그림**으로 바꿔 두고 `wp:docPr descr="slot:<열쇠>"` 로 표시한다. 채울 때 **바이트만** 갈아
끼우므로 자리·크기·덧그림(블록도 위 표시, OSD 키 위 빨간 상자)은 원본 그대로 남는다.
그림이 없는 칸은 그 그림을 지운다(회색 상자가 인쇄되면 안 된다).
회사 공통 정의 그림(시야각·응답속도·측정 장치·9점 균일도·온습도·불량 그림·RoHS·머리글 워터마크)은
양식에 그대로 남긴다. 그림판 OLE 원본(편집용 바이너리 3MB)은 떼고 미리보기 그림만 남겼다.

## 앱 값 연결 (`PS_AUTO`, js/76 — 데이터)
출처를 앞에서부터 시도한다. 고객 요구인 Customer SPEC 이 PARTS 패널 라이브러리보다 먼저다.

- 표지·머리글: Summary 모델 카드(지금 제품구분자) KTK PN·모델명, 고객 PN = **Project list `pn`** → 모델 카드 고객모델명
- `SG PN` 머리글 낱말: 고객사 이름으로(`PS_CUST_PN_LABEL`, 데이터)
- 부품 표: Project list(panel·panelMfr·adbd·adFw·bluDriver·tsp·touchCtrl·touchFw) → 주요자재 → PARTS 라이브러리 Brand
- Scope 글·Features 1: 글 틀 `PS_TEXT` + 모델명·인치·지원 해상도 중 최대
- 인증 CB/UL/CE/FCC: Project list 인증 칸
- 패널 화면 사양 14줄: PARTS PANEL 라이브러리 항목 + 광학은 Customer SPEC
- 시야각·BLU·절대 최대 정격: PARTS PANEL / 터치 표: PARTS TOUCH CTRL + Project list(touchFw·vidPid·glassType·airGap)
- 개정 이력 표 R1~R5: **각 리비전에 적어 둔 값**을 읽어 온다(`window._docRevisionFields`), 날짜는 그 리비전의 ISSUE DATE
- VCP 제목: `<고객사 앞부분> VCP Specification`

앱에 **없는** 칸 — 전원 커넥터 PN·케이블, 타이밍 표(도트 클럭·싱크), A/D 보드 커넥터 표·핀배치 10장,
컨버터 커넥터, OSD 메뉴 동작, VCP 표, 터치 기계·성능 일부. → **[📂 불러오기]** 로 기존 사양서를 읽어 채운다.

## 불러오기 규칙
- 앱이 아는 칸은 **앱 값이 이긴다**(앱 값이 비었을 때만 불러온 값). 빈 값은 저장하지 않는다.
- 자리 맞추기는 **빈 줄을 뺀 "내용 요소" 순서**로 한다 — 같은 계열이라도 빈 줄 개수가 다르다
  (실측: Upper 는 블록도가 커서 그 아래 빈 줄 4개를 지워 뒀다. 본문 번호로 읽었더니 공통 글 일치율이 15%).
- 같이 가져오는 것: 그림 바이트 + **원래 크기(cx,cy)·떠 있는 그림 위치(ph,pv)** + **쪽 맞춤 빈 줄 수(layout)**.
  이것들이 없으면 다른 원본의 그림이 양식 상자에 맞춰 줄고 쪽이 하나 밀렸다(실측).
- 공통 글 **일치율**을 같이 돌려준다 — 90% 아래면 화면이 경고한다(다른 계열 문서일 수 있다).

## 실제 프로젝트 확인 (2026-11-24, 백엔드 재시작 후)
⚠️ 이 절엔 실제 PN·부품명을 적지 않는다(저장소 공개) — 값은 회사 PC 의 프로젝트에서 본다.
한 고객 프로젝트(제품구분자 3개 = 원본 사양서 3개)에서 구분자마다 고객 PN 이 원본 파일과 그대로 맞물렸다.
터치 있는 구분자에 원본 사양서를 진짜 경로로 불러오고(백엔드 읽기 + NAS 그림 9장 업로드) [💾 원본저장]을 눌러
내려받은 파일을 원본과 비교 — **글 문단 수 같음, 쪽 맞춤 빈 줄 동일, 쪽 수 같음(22=22)**.
다른 곳은 전부 "앱 값이 이긴" 칸이다. 그중 **앱 데이터와 원본이 다른 종류**(어느 쪽이 맞는지는 사람이 정한다):
- 시야각·Display Colors — PARTS 패널 라이브러리 값이 원본과 다르다
- Scaler 보드 이름 끝자리·터치 컨트롤러 이름 꼬리·터치 F/W — Project list 값이 원본과 다르다
- 전원 표기 방식(Project list 는 'xxV=x.xA' 꼴) · 색좌표 원본은 ± 공차까지 적혀 있다
- 원본 Topper 판은 KTK PN 이 **다른 구분자의 PN** 으로 적혀 있다(원본의 복사 실수로 보인다 — 앱 값이 맞다)

그 과정에서 고친 것:
1. 앱 값의 **모양**을 문서 칸에 맞춤(`PS_FMT`, 데이터) — `X=0.305` → `0.305`, `400 ~ 450 nits (min ~ max)` → `400 ~ 450cd/m2`,
   `6850K`·`WCG (NTSC 90%)` → 숫자만(단위는 옆 Unit 칸에 이미 있다), `75` → `Min = 75`.
2. 제조사 정식 이름(회사명 + Corporation)이 좁은 Vendor 칸에서 두 줄로 접혀 **문서 전체가 한 쪽 밀렸다**(22→23쪽) → 짧은 이름 표 `PS_VENDOR_SHORT`.
3. Project list 의 `X`(없음)를 '터치 있음'으로 읽어 터치 없는 구분자가 터치 판이 됐다 → `_isNone`, 컨트롤러가 없으면 F/W 도 '-'.
4. BLU 전류·전압·전력은 라이브러리 값 하나로 Min/Typ/Max 중 어느 칸인지 몰라 **연결을 뺐다**(라이브러리 전압 값은 원본의 Max 칸 값이었다).
5. Scope 는 제품 인치(32”), Features 첫 줄은 **패널 원래 해상도**(지원 해상도 중 최대 — 받기만 하는 4K@30 — 를 집으면 틀린다).
6. ⚠️⚠️ **Document 페이지 편집이 저장 대상으로 표시되지 않던 버그**(js/67·js/69, 처음부터) — `_markDirty` 가 앱에 **없는** `window.markUnsavedChanges` 를 불렀다.
   불러온 칸 602개·그림 9장이 메모리에만 있고 자동저장이 건너뛰는 것을 실제 프로젝트에서 발견했다(다른 탭 편집이 우연히 같이 저장될 때만 실렸다).
   → `_markNonGanttDirty`(js/04a). 하네스가 이걸 본다(되돌리면 정확히 그 1건 실패).

7. ⚠️⚠️ **첨부 이름에 모델이 없어 다른 모델의 그림을 덮어썼다**(js/67 `_docAttachAdd`, 모든 Document 서식 공통) —
   첨부 폴더는 프로젝트에 하나인데 이름이 `날짜_서식_칸_파일` 이라, 같은 날 두 번째 모델을 불러오자 첫 모델의 블록도·외형도가
   같은 이름으로 덮였다(세 문서가 마지막 모델 그림 하나를 가리켰다 — 저장 전에 발견). → 이름에 `_dataKey`(회차·모델)+리비전을 넣는다
   (`날짜_product-spec_MVD_R1_img_block_…`). 하네스가 이름을 본다. 옛 이름 파일은 NAS 에 남아 있다(참조 없음, 지우지 않았다).

이어서 사람 요청으로 **세 구분자 모두 불러와 저장**했다 — 다시 읽어 칸·그림·쪽 맞춤이 구분자마다 들어 있고 간트 등 나머지가 그대로인 것,
NAS 에 올라간 블록도가 구분자마다 원본의 그 그림(바이트 크기 일치)인 것까지 확인.

(처음 확인 때는 저장하지 않았다 — 저장 호출이 권한 확인에서 막혔고, 사람이 "저장까지 해줘" 한 뒤에 저장했다.)
그 프로젝트의 NAS `DOCUMENT/<프로젝트>/PRODUCT SPEC/attach` 에는 그때 올린 그림 9장이 남아 있다(다시 불러오면 같은 이름이라 덮어쓰기를 묻는다).

## PARTS 라이브러리 연결 (2026-11-24 2차) — 실제 값 대조로 고른 것만
실제 프로젝트의 저장된 사양서 값(원본에서 불러온 것)과 그 제품 부품의 PARTS 기록을 칸마다 대조해, **값이 맞는 칸만** 이었다.

**부품의 기준은 BOM** (2026-11-24 사용자 결정: "BOM 정보가 실제 정보임")
부품 표 이름·PARTS 기록 찾기·터치 장 유무를 전부 **BOM → 이 모델 카드 주요자재 → Project list** 순서로 본다.
- BOM(`tabData.bomByUnit[모델]`)에서 부품 종류는 내역 앞 구분자(`LCM IPS>`·`PBA-AD>`·`PBA-CNV>`·`PBA-T>`·`TSP …>`) 또는
  자재그룹으로 가른다 — `PS_BOM_PARTS`(데이터). 보드는 자재그룹이 모두 'BD 반제품/PBA' 라 **구분자로만** 가른다(LED 보드와 섞이지 않게).
  부품명은 사내 자재그룹 규칙 그대로 `_bomPartNameOf`(js/56). 가장 얕은 단계의 행을 쓴다.
- BOM 을 받았는데 그 부품이 **없으면 거기서 끝**('-', 기록 없음) — 주요자재로 넘어가지 않는다. 터치 없는 모델 카드에
  첫 모델에서 **복사된** 터치 컨트롤러 주요자재가 남아 있었는데, 그걸로 판정하면 터치 장이 생긴다(하네스가 본다 — 이 규칙을 빼면 그 1건 실패).
- BOM 을 안 받은 모델은 주요자재(품목 코드 먼저) → Project list.
- 각 출처에선 **품목 코드 먼저** 찾는다 — 라이브러리마다 이름 적는 법이 달라 이름으로는 터치 컨트롤러를 못 찾았다.

실측(한 고객 프로젝트, 모델 3개): BOM 은 세 모델 모두 원본 사양서와 같은 부품이었다. 반면 Project list 는 AD 보드를 **다른 보드**로,
주요자재는 패널을 **다른 패널**(끝 글자 다름)로, 터치 없는 모델 카드는 복사된 터치 컨트롤러를 들고 있었다.
⚠️ 특히 패널 — 주요자재 쪽 이름으로 찾은 라이브러리 기록은 **다른 패널**이라 시야각이 원본과 달랐다. BOM 의 패널로 찾으니
라이브러리에 그 패널 기록이 따로 있었고 **시야각까지 원본과 같아졌다**(앞서 '데이터 차이'로 적었던 것의 정체).

**새로 이은 칸** — 터치 장 기계(가로·세로·두께)·성능 7줄·전원(전압·전류, `'5V @150mA'` 쪼개기)·컨트롤러(`제조사 / 품목코드`)·
제조사, BLU LED 전류 Typ, 균일도 폴백(패널 White Variation), 컨버터 입·출력 커넥터 모델명(불러온 값이 없을 때만).
실측: 이은 칸 중 원본과 그대로 같은 것 13칸, 다른 것은 표기 차이(쉼표 앞 공백·'10 Touch' 접두어)와 데이터 차이(가장자리 정확도)뿐.

**안 잇는 것과 이유**
- BLU 전압·전력 — 라이브러리 값 하나가 원본의 Max 칸(전압)·Typ 칸(전력)에 각각 맞았다. 칸이 일정하지 않아 잘못 들어갈 수 있다.
- A/D·컨버터 커넥터 표·핀배치 — 라이브러리엔 커넥터가 자유 글('6 Pin Inverter control (…), EXT OSD KEY (…)')로만 있고 핀 배정이 없다.
- 컨버터 커넥터의 기판 표시(J1)·제조사 — 라이브러리에 없다(모델명만 넣는다).
- Touch Technology — TSP 라이브러리는 'Capacitive', 원본은 'ITO PCT'(같은 뜻을 다르게 적는다).
- Touch Sensor 제조사 — TSP 라이브러리 Brand 는 유리 제조사, 원본은 공급사(Kortek). 뜻이 다르다.
- 타이밍 표 — 라이브러리에 없다.

**데이터 쪽에서 볼 것** (값은 적지 않는다 — 회사 PC 에서 확인)
- Project list 의 AD 보드·주요자재의 패널이 BOM 과 다르다(문서는 이제 BOM 을 따르므로 문서엔 영향 없음 — 다른 화면이 그 값을 쓴다)
- 터치 없는 모델 카드에 복사된 TOUCH CTRL 주요자재가 남아 있다
- 터치 가장자리 정확도: 라이브러리 값과 원본 값이 다르다

## BOM 커넥터 (2026-11-24 3차) — 설치지점(EBORT)·품번·제조사
BOM 엔 보드 **바로 아래** 커넥터 행마다 설치지점(J1·J11·SW1…)·품번·제조사(MFRPN)가 있다. 원본 사양서의
'A/D Board connection' 표와 컨버터 커넥터 문장이 바로 이 정보다.
- **컨버터 입·출력 커넥터 문장** — `J1 : <품번> (<제조사>)` 꼴로 BOM 에서 만든다. 어느 커넥터가 입력/출력인지는
  PARTS 라이브러리의 입력/출력 커넥터 품번과 **앞부분이 같은 것**으로 가린다(BOM 이 정확한 품번, 라이브러리는 끝에
  글자가 붙어 있기도 하다). 실측: 원본 문장과 글자까지 같았다.
- **A/D Board connection 표** — 새 프로젝트면 BOM 커넥터로 Symbol·Parts Number·Manufacture 를 채운다(Description 은
  BOM 에 없다). 설치지점은 자연 정렬, 번호가 이어지는 스위치는 `SW1~4` 한 줄(원본 모양), 띄엄띄엄인 `J1,J7` 은 두 줄.
  BOM 커넥터가 표 줄 수(10)보다 많으면 10번째 칸 출처에 "N개 중 10개만"을 적는다(숨기지 않는다).
- **BOM 대조** — 사람이 적었거나 불러온 표 값이 BOM 과 다르면 그 칸 아래 빨간 글씨로 `BOM: <값>` 을 띄운다
  (화면 전용 — 인쇄·원본저장엔 안 나온다, 고치지도 않는다). 입구는 js/67 의 `DOC_CELL_CHECK[서식id]`(칸, 값) 하나.
  실측으로 원본 사양서에서 핀 수가 다른 품번, **두 커넥터 품번이 뒤바뀐 줄**, 다른 품번·제조사를 찾았다.
- 데이터: 커넥터 구분자 `PS_BOM_CONN_SEPS`(CON·JACK·SWC), 제조사 표기 `PS_MAKER_EN`(원본에서 확인된 것만 —
  없는 이름은 한글 그대로). 자재그룹 규칙에 부품명 자리가 없으면 품번처럼 생긴 첫 낱말(영문+숫자 5자 이상).
- 하네스: 표 채우기·LED 보드/컨버터 커넥터 안 섞임·컨버터 문장·대조 경고. '보드 바로 아래만' 규칙을 깨면
  컨버터 커넥터가 A/D 표에 섞이는 것으로 실패한다.

## 불러오기 없이 새 프로젝트로 (2026-11-24 4차)
사양서를 불러온 적 없는 다른 프로젝트(BOM·Customer SPEC·Project list·PARTS 가 있는 27인치 모델)로 앱 정보만으로
만들어 봤다(저장 안 함 — 열지 않고 파일을 읽어 계산만). 자동 칸 **87/129 → 106/129**.
- **패널 사양 칸 9개가 통째로 비었다** — BOM 패널 이름 끝에 패널 리비전이 괄호로 붙고(`…-N20(B10)`) PARTS 라이브러리는
  기본 이름으로 적혀 있어 못 찾았다. 그대로 못 찾을 때만 꼬리를 떼고 한 번 더 찾는다(`PS_LIB_NAME_TRIM`, 데이터).
  그렇게 찾은 칸은 출처에 `PARTS ▸ PANEL (찾은 이름) ▸ …` 로 보인다 — 리비전이 다르면 사양이 다를 수 있으니
  사람이 볼 수 있게. 공용 매처(js/22d `_epFlexibleFind`)는 안 건드렸다(쓰는 곳이 10곳 넘는다).
- **전원 Consumption·Connector PN** — Customer SPEC 에 있었는데 안 이어 두었다.
  - Consumption: 'Power estimation (Max. W)' 의 첫 하위 줄(**라벨이 하위 이름 'LCD Monitor'** — js/66 이 하위 이름을
    라벨로 쓴다, 처음엔 항목 이름으로 찾아 빈칸이었다) 숫자만 `PS_TEXT.pwrCons`(`{w}[W] Max (Display only)`) 모양으로.
    ⚠️ Customer SPEC 은 **추정치**라 실제 사양서 값과 다를 수 있다(실측: 원본 문서보다 3W 컸다) — 출처가 화면에 보인다.
  - Connector PN: 'Input voltage' 의 `/` 뒤에서 핀 수 표기(`6P_`)를 떼고 `제조사 품번`. 실측 원본과 글자까지 같았다.
- 여전히 앱에 없는 것: Terminals PN·Cable·Features 2/4·LED light bar 문장·A/D 커넥터 제목(J1 : 4 Pin External Power —
  핀 용도는 BOM 에 없다)·A/D 표 Description·핀배치·타이밍·OSD·VCP.
