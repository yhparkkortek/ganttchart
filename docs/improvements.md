# 🛠 개선 사항 메모

**이 문서는 "무엇을 고쳤고, 다음에 무엇을 고칠 만한가"의 목록이다.**
상세한 원인·설계는 각 주제 문서에 있고 여기엔 **한 줄 요약 + 숫자 + 가리키는 곳**만 적는다.

- ⚠️ **숫자 없는 항목은 적지 않는다.** "느린 것 같다"는 개선 항목이 아니라 **측정할 일**이다.
- ⚠️ **"안 하기로 한 것"도 이유와 함께 남긴다** — 안 적으면 다음에 또 똑같이 검토한다.
- 측정값은 전부 **같은 기계·같은 순간·최솟값** 기준이다(1회 측정은 2~3배 흔들린다).

## ✅ 2026-11-05 — Gantt 표 렌더 (완료, `b2ad463` + `282639f`)

신고: *"간트차트가 오히려 느려졌음 / 행 잡고 이동도 느리고 펼치고 접는 것도 느리고 전반적으로 느림"*

실측으로 찾은 범인은 **`renderTable()` 하나**였다. 사람이 느끼는 동작(행 이동·펼치기·접기)이
전부 그 함수로 흘러들어가고 있었고, 그 함수는 **보이든 안 보이든 행 전부를 다시 만들고** 있었다.

| 동작 (LNW_STELLAR32 908행, 전부 펼친 상태) | 전 | 1차 | **지금** |
|---|---|---|---|
| **행 놓은 뒤 멈춤 (드래그 이동)** | 2,160~2,745ms | 1,614~1,920ms | **192~253ms** |
| `renderTable()` 한 번 | ~2,600ms | 1,146ms | **77ms** |
| 전부 펼치기 | 949~2,027ms | ~900ms | **163ms** |
| 가지 전체 펼치기/접기 | 1,256ms | 108ms | **27ms** |
| 한 행 접기/펴기 | 390~467ms | 238ms | **33ms** |
| tbody HTML | 8.71MB | 7.03MB | **0.45MB** |
| DOM 노드 | 44,748 | 44,848 | **4,208** |
| 칸을 실제로 만든 행 | 908 | 908 | **57** |

무엇을 했나 — 상세는 **`docs/gantt-internals.md`** 맨 아래 두 절:
1. `toggleWbsBranchFull()` 이 `renderTable()` 을 안 부른다(바뀌는 건 화살표 둘뿐).
2. 행마다 똑같던 **inline style 3.01MB → 1.29MB**(styles.css 클래스로).
3. 칸마다 다시 하던 열 이름 정규화(한 번 렌더에 36,000번) → `_rtCtx` 에 한 번만.
4. **스크롤 가상화** — 화면 밖 행은 높이만 가진 자리표시, 스크롤을 따라 채운다.

같이 막은 조용한 오답 두 가지 — 인쇄 복제 전 `_ganttHydrateAll()`(안 하면 종이에 빈 줄),
"표시 No." 를 `tr.dataset.vno` 에도 적기(안 하면 AI 문답이 화면 밖 행을 못 찾는다).

## 📌 다음에 할 만한 것 (근거 있는 것만)

### 1. 검색 중에는 가상화 이득이 사라진다 — 실측 837행 ≈ 0.6초
`js/26` 은 일치한 행을 **전부** 채운다. 글자 하이라이트를 칸 안에 넣어야 하기 때문이다.
2026-10-28 이전과 같은 비용이라 **느려진 건 아니지만**, 900행 프로젝트에서 검색 한 번이면
표가 다시 무거워진다(다음 `renderTable()` 이 리셋할 때까지).

- 하려면: `_ganttHydrateRow` 에 **"채운 직후 훅"** 을 두고 js/26 이 거기서 하이라이트를 다시 입힌다.
  그러면 화면 밖 일치 행은 안 채워도 된다.
- ⚠️ 훅 없이 그냥 "안 채우기"만 하면 **스크롤해서 나타난 행에 하이라이트가 빠진다** — 조용한 오답.

### 2. inline 이벤트 핸들러가 아직 1.73MB (표 HTML 의 20%)
행마다 `onclick`·`ondblclick`·`onblur` 가 **29개**씩 붙는다. 특히 날짜 칸 두 개의 `onclick` 은
여러 문장짜리 긴 문자열이라 **행당 ~400바이트씩** 차지한다.

- 위임 핸들러로 바꾸면 ① 파싱 바이트가 줄고 ② 더 큰 것 — **행 인덱스가 HTML 에서 빠진다**.
  지금은 `${i}` 가 핸들러마다 박혀 있어서, 행을 **옮기면 그 전부를 다시 써야 한다**.
  그래서 드래그 이동이 "DOM 행을 옮기기" 가 아니라 "표를 다시 만들기" 다.
- 선례: `js/55` Project list 가 같은 이유로 칸마다 달던 onclick 을 위임으로 바꿨다.
- ⚠️ `onblur` 는 위임하려면 `focusout` 으로 받아야 한다(버블링 안 되는 이벤트).

### 3. `renderTable()` 호출지가 49곳
가상화로 한 번이 77ms 까지 내려와 급하진 않지만, **한 곳 줄일 때마다 그대로 체감**이다.
고칠 때는 "이 동작이 정말 표 전체를 다시 그려야 하나"를 먼저 물을 것 —
`toggleWbsBranchFull` 이 그 질문 하나로 1,256ms → 108ms 가 됐다.

### 4. 프로젝트 JSON 9.9MB 중 `_mailRaw`(메일 원문)가 6MB
`docs/gantt-internals.md` 에 이미 적혀 있는 남은 병목. 열기 다운로드·저장 업로드가 이 크기에
비례한다(네트워크). `js/54-mail-body-store.js` 가 본문을 밖으로 빼는 중 — 진행 상태를 먼저 잴 것.

### 5. 자동화 테스트 러너가 없다
`tests/` 에 하네스가 20개 넘게 쌓였는데 **러너가 0개**라 사람이 매번 골라서 돌린다.
브라우저 하네스는 프로젝트를 열어야 해서 자동화가 쉽지 않지만, **node 로 도는 것들**
(`storage-adapter` · `bom-part-lookup` · `daily-report` · `gantt-excel-meta-loss` 등)은
한 줄로 모아 돌릴 수 있다.

## 📏 측정할 때 두 번 속았다 — 다음 사람에게

- **1회 측정은 2~3배 흔들린다.** 이 PC 는 다른 작업이 같이 돌아서 *"내용을 지웠는데 더 느려졌다"*
  (−1,299ms) 같은 값이 실제로 나왔다 → **변형을 번갈아 돌리고 최솟값**을 쓴다.
- **longtask PerformanceObserver 는 30초짜리 엉터리 값**을 준다(브라우저가 주변 작업까지 한 덩어리로
  묶는다) → 16ms 탐침을 걸고 **깨어난 시각이 얼마나 밀렸는지**를 본다.
- **브라우저 창이 숨어 있으면 숫자가 거짓이다** — `requestAnimationFrame` 이 멈춰 스크롤 채우기가
  돌지 않고, 하네스가 그 자리에서 영영 기다린다(실제로 한 번 멈췄다).
- **inline 에 적혀 있다고 그게 적용되던 값이 아니다** — 레벨1 날짜 칸의 `font-weight:normal`,
  상세내용 칸의 `font-size:11px` 는 `!important` 규칙에 눌려 **원래부터 죽은 선언**이었다.
  그걸 "기대값"으로 삼으면 거꾸로 모습이 바뀐다 → **기대값도 실측해서 적을 것**.
