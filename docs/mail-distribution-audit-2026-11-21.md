## 3. 재편안 — "메일 하나 · 판정 하나 · 쓰기 하나 · 기록 하나"

### 3-1. 원칙
1. **결정론 먼저, AI 는 후보를 고르되 증거를 대야 하고, 자동배치는 코드가 결정한다**(CLAUDE.md 최우선 방향 그대로).
2. **배분 단위는 "프로젝트 → 모델(제품구분자)" 두 단계.** 가족 식별(고객·프로젝트)은 결정론으로 거의 맞는다. 모델 식별자가 본문에 없으면 모델을 **추측하지 않고** 프로젝트에만 붙인다(`unit:null`). 형제 프로젝트가 **별도 파일**인 지금 구조에선 이 단계를 표현할 자리가 없다 → §4 질문 1.
3. **메일의 열쇠는 하나** — 백엔드가 `Message-ID`(없으면 date+from+subject 의 sha1)를 `key` 로 내려주고, 수집·큐·보관함·행(`_mailKey`)·원장·근거·NAS 이동이 전부 그것으로 중복을 가른다. `fileName` 은 표시용으로만 남긴다.
4. **쓰기 입구는 하나** — `placeMailTask({key, task, target, unit, how, by})`: 중복 검사 → 행 생성 → 원장 → 교정/경로 기록 → 토픽 신호 → NAS 이동 → 저장 **확인 뒤** 상태 변경. 18개 입구가 전부 이것을 부른다. 헤드리스 PATCH 3벌·재배치 로컬 큐·`inboxPlaceToCurrent` 의 저장 생략은 없어진다.
5. **팀 공용 기록 한 곳**(`App_Config/MailRoutes/<YYYY_MM>.json`, 월 1파일·더하기만): 확정 배분·사람 교정·되돌림. 지금의 로컬 `gantt_mail_route_history_v1`·`gantt_ai_reassign_queue_v1`·`aiLearning` 의 no_match 더미를 대체한다. 근거층은 이 기록만 읽는다 — PC 가 달라도 같은 사실을 본다.
6. **후보 설명은 식별자만** — 색인 `keywords` 는 고객모델명·KTK PN·프로젝트코드·관리번호·사람이 적은 메일키워드로 한정. SAP 자재내역·사람 이름·전시회·범용어·자동 누적 토큰은 뺀다. 토픽 프로파일은 요약·단계·판별단서만 프롬프트에 쓰고 **자동 키워드 누적(`_tpAppendMailSignal` 의 제목 토큰 밀어넣기)은 끈다.**
7. **AI 단독 "상" 은 자동배치 근거가 아니다.** 자동배치 = (고유 식별자 정확 일치) ∨ (사람이 확정한 스레드) ∨ (AI 상 + 인용 검증 통과 + 형제 후보와 구별하는 고유 토큰이 인용문에 있음). 그 외는 대기. 복수 후보 동시 자동배치는 **없다**(대기 + 후보 목록).

### 8-6. 📨 제목 먼저 · 📐 인치 · ⚡ 재판정 속도 (같은 날, 남은 대기 96건 재생)

- **제목 먼저**(`P.subjectFirst`): 제목만으로 결정론(식별자·단독 가족·가족 인치·가족 대표)이 한 곳을 가리키면 그걸로 정한다

  "다른 프로젝트 단어도 여럿" 충돌이었다. 제목 판정에선 다른 프로젝트 단어가 **하나만** 있어도 충돌(제목은 짧다) —
  `ZITRO ICONI & LnW STELLAR & LnW OBSIDIAN…` 이 한 곳으로 가지 않게.

- ⚡ **속도**: 식별자·가족·가족 토큰을 후보 목록마다 한 번만 만든다(`prepared`, 열쇠 = 배열 + id·updated_at·키워드 수 + 가족 설정 버전)

  5건마다 화면에 양보한다. 배경 스윕은 `routing.v === MAIL_ROUTING_RULE_V` 카드를 건너뛴다 —
  ⚠️ **판정 규칙을 바꾸면 `RULE_V` 를 올릴 것**(안 올리면 옛 판정 카드가 배경에서 다시 안 보인다; 버튼은 늘 전부 본다).
- 사유 글이 재판정마다 '🧭 · 🤖 (이전 사유 전체)' 로 겹겹이 길어지던 것 → `aiReasonOnly`.
