> **이 문서는 코드가 아니라 검토서다.** 아직 아무것도 구현하지 않았다.

## 1. 주간 보고와의 관계 — 부모-자식이 아니라 **직교하는 두 축**

### 1-1. 지금 주간보고가 실제로 하는 일

읽어 보니 주간보고는 "사람이 쓴 보고서"가 아니라 **간트 일정의 주간 단면도**다.

| 항목 | 주간보고(js/20) | 일일보고(만들 것) |
|---|---|---|
| 축 | **프로젝트 1개 × 주 1개** | **사람 1명 × 날짜 1개** |
| 범위 | 지금 열린 프로젝트만 | 그 사람이 손댄 모든 프로젝트 |
| 출처 | `globalData`에서 **계산**(저장 안 함) | 사람이 **쓴 글**(저장해야 함) |
| 내용 | 이번주 실적 / 다음주 계획 / 문제점 표 | 오늘 한 일 / 내일 할 일 / 막힌 것 |
| 입력 | 없음(간트 칸을 고치는 게 입력) | 하루 1회 |
| 출력 | PPT·인쇄 | 화면·엑셀 |

**그래서 "일일보고를 모으면 주간보고가 된다"는 성립하지 않는다.** 주간보고는 프로젝트별로 PPT 1장이 나와야 하고, 일일보고는 사람별로 쌓인다. 5명이 3개 프로젝트를 섞어 하면 일일보고 5건을 모아도 프로젝트별 PPT가 안 나온다.

### 1-2. 그런데 **두 번 쓰게 만들면 안 된다** — 접점은 딱 한 곳

주간보고의 "문제점 및 Issue" 표는 **`colIdx.content` 칸의 `[문제점]`/`[대책]` 줄만** 읽는다(`wrExtractIssue`). 여기가 유일하고 충분한 접점이다.

> **일일보고에 이슈를 쓰면 → [이 이슈를 업무에 반영] 버튼 1개 → 그 업무 행의 `content` 칸에 `[문제점]`/`[대책]` 줄을 추가 → 주간보고에 자동으로 나타난다.**
>
> **js/20은 한 줄도 안 고친다.** 주간보고는 그 줄이 어디서 왔는지 알 필요가 없다.

이게 이 설계에서 제일 중요한 판단이다. 대안(주간보고가 그 주 일일보고 파일들을 직접 읽어 표에 합치기)은 ① js/20을 고쳐야 하고 ② 프로젝트축↔사람축 변환을 주간보고가 짊어지고 ③ PPT 출력 경로까지 영향이 간다. **버튼 한 개로 끝나는 쪽이 압도적으로 싸다.**

반대 방향(주간보고 → 일일보고)은 **연결하지 않는다.** 주간은 파생 뷰라 되돌려 쓸 원본이 없다.

## 2. 간트 데이터와의 관계 — 자동으로 끌 것 / 사람이 쓸 것의 경계

### 2-1. 자동으로 끌 수 있는 것 (AI 없이, 결정론)

| 끌 것 | 출처 | 비고 |
|---|---|---|
| 오늘 **예정된** 내 업무 | `globalData`의 leaf 행 중 `_calcStartTs ≤ 오늘 ≤ _calcPlanTs` + 담당자=나 | 주간보고 `wrClassifyTasks`와 같은 방식, 범위만 하루 |
| 오늘 **손댄** 업무 | `changeLogs`에서 `userName`=나 + `time`이 오늘 | 프로젝트 파일 안에 이미 있다 |
| 업무명·기간·상태 | `wrTaskName(row)` / `_calcStartTs` / `colIdx.status` | 재사용 |
| 프로젝트명 | `currentFileName` / `projectMeta` | |
| 지연 여부 | `_calcPlanTs < 오늘` && status≠완료 | 계산값 |

**이걸로 화면에 체크박스 목록을 띄우는 게 "1분 동선"의 핵심이다.** 사람은 자유 타이핑을 하는 게 아니라 **체크하고 한 줄 덧붙인다.**

### 2-2. 사람이 반드시 직접 써야 하는 것

| 쓸 것 | 왜 자동이 불가능한가 |
|---|---|
| **이슈 / 막힌 것** | 간트에 "막혔다"는 상태가 없다. 지연은 결과지 원인이 아니다 |
| **내일 할 일** | 간트의 내일 일정은 *계획*이고, 사람의 내일 할 일은 *의도*다. 보통 다르다 |
| 오늘 한 일의 **한 줄 요약** | 업무명은 "PROTO A 조립"이지만 보고는 "조립 중 체결부 간섭 발견" |
| **일 종류**(근무/휴가/반차/출장/교육) | 알 방법이 없다(§6-3) |

### 2-3. ⚠️ 경계에서 생기는 함정 — "나"를 어떻게 알아보나

이게 가장 조용히 틀릴 자리다. 세 이름 체계가 서로 다르다.

| 어디 | 값의 모양 | 예 |
|---|---|---|
| `window.currentUserName`(NAS 모드) | **사내 계정 id** | `KKR034` 같은 것 |
| 간트 행 `colIdx.assignee` | **사람이 엑셀에 쓴 자유 텍스트** | `박용훈`, `박PM`, 빈칸 |
| `changeLogs[].userName` | 저장 시점의 `currentUserName` | 과거 Drive 시절엔 **구글 계정 표시명**이 섞여 있다 |
| `/telegram/members[].name` | 사람이 등록한 이름 | `박용훈` |

`docs/purchase-order.md`에 이미 같은 함정 기록이 있다 — *"WEMPF는 계정 ID가 아니라 한글 실명(KKR034 ↔ 박용훈)"*.

→ **명단(roster)을 데이터로 두고 거기서 잇는다.** 하드코딩 금지, 코드에 이름 금지.

```
App_Config/DailyReport/_roster.json   (쓰는 사람: PM 한 명 — 관리자 게이트)
{
  "savedAt": "...",
  "members": [
    { "key": "<계정id>", "name": "<실명>", "aliases": ["<약칭>", "..."],
      "team": "개발3팀", "tgChatId": "...", "email": "...",
      "active": true, "leave": [{"from":"2026-11-10","to":"2026-11-12"}] }
  ]
}
```

- `key`는 계정 id(기계가 아는 값) — 이걸로 **내 파일**을 정한다.
- `aliases`는 **간트 담당자 칸 매칭용 어휘**다. 못 맞추면 자동 초안이 비는 것뿐이고(조용한 오답이 아니다), 사람이 직접 쓰면 된다. 매칭 실패는 `_issueLog`로 남겨 **별칭을 늘릴 신호**로 쓴다(CLAUDE.md "학습으로 업그레이드" 1·2번).
- `tgChatId`/`email`은 `/telegram/members`에서 **가져와 채우기** 버튼으로 복사(두 벌 관리를 사람이 안 하게).

## 3. 저장 위치와 동시성 — **쪼갠다. 한 파일 upsert는 하지 않는다**

### 3-1. 결론: 사람 × 날짜 = 파일 하나

```
App_Config/DailyReport/_roster.json                 ← PM만 씀
App_Config/DailyReport/_nonworkdays.json            ← 앱이 씀(§6-2)
App_Config/DailyReport/2026-11/2026-11-04__<계정id>.json   ← 그 사람만 씀
App_Config/DailyReport/2026-11/2026-11-04__<다른계정>.json
```

**불변식 하나: 한 파일에는 쓰는 사람이 한 명뿐이다.**

오늘(2026-11-04) `project_index.json`의 `projects`가 통째로 사라진 사고의 모양은 이랬다 — ① 여러 주체가 ② 같은 파일을 ③ 읽고-고쳐-통째로 쓰는데 ④ 읽기가 옛 사본이었다. **쓰는 사람을 1명으로 만들면 ①이 사라지고, 사고의 전제가 성립하지 않는다.**

일일보고는 운 좋게 데이터 자체가 사람·날짜로 자연 분할된다. **이 운을 버리고 팀 1파일로 합칠 이유가 없다.**

### 3-2. 왜 "팀 하루 1파일 upsert"를 버리는가

| | 사람×날짜 파일 | 팀 하루 1파일 upsert |
|---|---|---|
| 동시 쓰기 | **구조적으로 불가능** | 5명이 17시에 몰린다 |
| 쓰기 방식 | **통째 쓰기**(읽기 불필요) | 읽고-고쳐-쓰기 |
| 캐시 lost update | 읽지 않으니 해당 없음 | **그 사고의 모양 그대로** |
| 하루 보기 | list 1 + get N(5) ≈ 6콜 | get 1콜 |
| 한 달 보기 | **list 1콜**로 전원·전일 목록 | get 20콜 |
| 남의 글 날림 | 불가능 | 가능 |

하루 보기가 1콜 → 6콜로 늘지만 고정비 61ms × 6 ≈ 0.4초다. **그 0.3초로 "남의 보고가 사라지는 사고"를 구조에서 지운다.** 바꿀 이유가 없는 거래다.

### 3-3. ⚠️ 그래도 남는 lost update 하나 — 같은 사람, 같은 날

내 파일을 **내가** 두 번 쓰는 길이 있다(두 PC / 두 창 / 다른 프로젝트를 열고 추가). 하루치에 업무를 **덧붙이는** 동작은 읽고-고쳐-쓰기가 된다.

지켜야 할 것:
1. **NAS GET에 캐시 금지** — `cache:'no-store'` + `_cb=` 난수 둘 다. (`no-store`는 그 요청만 막는다. 이미 캐시에 든 사본을 피하려면 URL이 달라야 한다 — 2026-11-04 실측)
2. 파일에 `rev`(정수)를 둔다. 쓰기 전에 다시 읽어 `rev`가 내가 본 값과 다르면 **덮지 않고** 최신본을 보여주고 "방금 쓴 내용을 다시 넣어주세요"로 말한다(js/55 `plSaveToNasJson`와 같은 패턴).
3. **빈 내용으로 덮어쓰기 거부** — 지금 파일에 항목이 N개 있는데 0개를 쓰려 하면 막고 `_issueLog`에 남긴다(`guardIndexWrite`와 같은 발상). 지우는 건 사람이 명시적으로 고를 때만.
4. 입력 중 초안은 **localStorage에 먼저**(`gantt_daily_draft_v1`), NAS 쓰기는 [저장]을 누를 때. 창이 닫혀도 글이 안 날아간다. → `STORAGE_REGISTRY`(js/34)에 `cls:'log'`로 등록.

### 3-4. 공용 NAS 파일 헬퍼가 필요하다 (선결 과제)

지금 `/nas/app/*`를 부르는 곳은 js/57(어댑터)·js/58(이사)·js/36(설정) 셋인데, **어댑터의 `readRel`/`writeRel`/`listRel`은 모듈 내부 함수라 `window`에 없다.** 일일보고가 자기 fetch를 또 쓰면 `no-store`·`_cb`·오류 분기를 **네 번째로 베끼는** 것이고, 그건 2026-11-04에 반복해 적힌 실패 모양이다(*"목록을 js/57로 베끼면 Drive에 하나 늘 때 NAS만 조용히 빠진다"*).

→ **js/57에서 `window.nasAppFile = { get, put, list, exists }`를 내놓는다**(상대경로 전용, `no-store`+`_cb` 내장, 403/404 구분). 10~20줄이고, 앞으로 생길 팀 공용 데이터가 전부 이걸 쓴다.

### 3-5. 모드 판정은 `window._storageMode()`로

CLAUDE.md 2026-11-04 항목: *"토큰이 있나로 드라이브 연동을 묻지 말 것 — NAS 모드에선 어댑터가 토큰을 가짜로 채운다."* 일일보고는 NAS 전용이므로 **`window._storageMode()`가 `nas`가 아니면 탭을 비활성**으로 두고 이유를 적는다(`_storeConnectHint()` 재사용).

## 4. 화면 — 입력은 **모달**, 집계는 **탭**

### 4-1. 왜 입력을 탭으로 안 하나

요구가 "하루치 입력이 1분 안에"다. 탭이면 ① 앱 열기 ② (NAS 연결) ③ 프로젝트 열기 ④ 탭 이동 ⑤ 입력. **③·④가 군살이다** — 일일보고는 프로젝트와 1:1이 아닌데 프로젝트를 열게 만들 이유가 없다.

→ **입력은 어디서든 열리는 공용 모달.** 들어가는 길 셋:
1. 헤더 버튼 `📔`
2. 집계 탭 안의 [✏️ 내 보고 쓰기]
3. **미작성 상태로 앱을 열면 1회 자동**(§4-4 — 충돌 주의)

집계(PM 보기)는 사이드바 새 탭 `daily` — 표가 크고 머물러 보는 화면이라 탭이 맞다.

### 4-2. 모달 동선 (목표 ≤ 1분)

```
┌ 📔 일일 업무보고 — 2026-11-04 (수)                          [✕]
│ 일 종류: (●근무) (휴가) (반차) (출장) (교육)      ← 휴가면 아래가 접힌다. 끝.
│
│ 오늘 한 일   [간트에서 불러오기 ▾ 자동 3건]
│   ☑ PROTO A 조립 검토   (STELLAR32)   + [한 줄 덧붙이기___________]
│   ☑ 고객 SPEC 회신      (STELLAR32)   + [__________________________]
│   ☐ BOM 단가 확인       (OBSIDIAN)
│   [+ 직접 추가]
│
│ 내일 할 일  [______________________________________________]
│
│ 막힌 것·이슈 [____________________________________________]
│   └ [이 이슈를 업무에 반영]  ← §1-2. 누르면 주간보고 문제점 표에 뜬다
│
│                              [임시저장(자동)]   [✅ 저장]
```

- 체크박스 3개 + 한 줄 = **클릭 4번·타이핑 1줄**. 이게 1분 설계다.
- 어제 쓴 "내일 할 일"을 오늘 "오늘 한 일" 후보로 **먼저 올려준다**(어제 파일 1건 읽기). 반복 업무를 다시 타이핑하지 않게 하는 장치다.
- 모달 컨벤션 필수(`docs/ui-conventions.md` §모달): `_makeDraggable` · `_bindClickToFront` · `bringModalToFront`, 박스에 `max-height:90vh`, 본문에 `flex:1; min-height:0; overflow-y:auto`. **`min-height:0`을 빼면 스크롤바가 안 생겨 [저장] 버튼에 손이 안 닿는다**(2026-11-04 🔑 모달 사고).
- 입력 항목은 코드에 박지 않는다 — `DAILY_FIELDS` / `DAILY_DAY_TYPES`(데이터). 항목을 늘리는 건 배열에 한 줄.

### 4-3. 간트 행에서 바로? — **1단계에선 안 한다**

행마다 📔 버튼을 달면 ① 하루 한 번 쓰는 걸 행마다 흩뿌리고 ② 다른 프로젝트 업무는 여전히 못 넣고 ③ 숨은 행은 `data-lazy` 자리표시라 `_ganttHydrateRow` 처리를 또 해야 한다(`docs/gantt-internals.md`). **모달의 "간트에서 불러오기"가 같은 일을 더 싸게 한다.**

### 4-4. ⚠️ 자동 열기 충돌

`STORAGE_POLICY.autoOpenProjectList`가 이미 앱을 열 때 프로젝트 목록 창을 띄운다(2026-11-04). 여기에 일일보고 모달까지 자동으로 뜨면 **팝업 두 개가 겹친다.** → 둘 중 하나만. 프로젝트 목록을 **닫은 뒤**에 띄우거나, 자동 열기를 포기하고 헤더 버튼에 **빨간 점**만 찍는다(후자가 안전). 데이터로: `DAILY_POLICY.autoOpenModal`(기본 false).

## 5. 집계·조회

### 5-1. 하루 보기 (PM의 기본 화면)

날짜 선택 → `list('App_Config/DailyReport/2026-11')` **1콜** → 파일명에서 `(날짜, 사람)`을 뽑아 그날 것만 `get` → 표.

| 사람 | 종류 | 오늘 한 일 | 내일 할 일 | 막힌 것 | 작성 |
|---|---|---|---|---|---|
| 박용훈 | 근무 | PROTO A 조립 검토 / SPEC 회신 | BOM 단가 | 체결부 간섭 | 17:42 |
| (ㅇㅇㅇ) | — | **미작성** | | | — |

- **미작성이 한눈에 보이는 게 이 화면의 핵심 가치다.** 명단(roster) × 그날 파일 존재 여부의 차집합.
- `mtime`이 목록에 같이 오므로 작성 시각은 **파일을 읽지 않고도** 표시된다 — 미작성 판정은 list 1콜로 끝난다.
- 표는 `table-layout:fixed`가 전역이라 **표 폭을 줘야 열 폭이 지켜진다**(`docs/ui-conventions.md`).

### 5-2. 기간 조회

달 폴더 list 1콜로 그 달 전체 격자(사람×날짜, 작성/미작성/휴가)를 먼저 그리고, **칸을 누르면 그때 `get`** 한다. 월 전체 내용을 미리 다 읽지 않는다.

### 5-3. 엑셀

**1단계는 출력만.** `js/04k`의 기존 스타일러를 쓴다. 되돌려 넣기(js/42 `PAGE_EXCEL_SPECS`)는 하지 않는다 — 엑셀에서 수정해 다시 넣으면 **남의 하루 파일을 내 브라우저가 쓰게 되고**, §3-1의 불변식이 깨진다. 이게 왕복을 안 붙이는 진짜 이유다.

내보낼 때 i18n: 시트명·머리글·행 라벨까지 `_t` 대상이다(`docs/ui-conventions.md`, 2026-10-20에 지적된 반복 누락).

### 5-4. 열람 범위

1단계는 **전원이 전원을 본다**(팀 5명, 서로 뭘 하는지 보는 게 목적). NAS ACL은 팀 폴더 단위라 어차피 파일 단위 숨김이 안 된다 — **"가릴 수 있다고 약속하지 않는다."** 민감한 걸 쓰는 칸이 아니라고 미리 말해두는 게 맞다. (§9-3 질문)

## 6. 미작성 알림 — 재사용 가능하지만 **그대로는 못 쓴다**

### 6-1. 기존 자산

| 자산 | 재사용 | |
|---|---|---|
| `send_telegram_msg` / `send_telegram_multi` | ✅ 그대로 | `parse_mode:HTML`이라 `<`·`&` escape 필수 |
| `/telegram/members` | ✅ chat_id 출처 | |
| `_scheduler_loop`(60초 틱) | ✅ 붙일 자리 | `_mail_watch_tick` 선례 |
| `lastFiredBucket` 중복방지 | ✅ 발상 차용 | 버킷키 `daily:<날짜>:<사람>` |
| `/schedule` 규칙 | ❌ | 고정 문구·고정 명단이라 "미작성자에게만"을 표현 못 한다 |

→ `_daily_report_tick()`을 **새로** 만들어 기존 루프에 붙인다(`_mail_watch_tick`와 같은 모양).

### 6-2. ⚠️ 휴일 판정 — 백엔드는 공휴일을 **모른다**

`KOR_HOLIDAYS`(2035년까지)는 **`js/04d`에만** 있다. `Holidays_Shared.json`은 *추가* 휴일뿐이다. 백엔드에 공휴일 배열을 복사하면 ① 하드코딩이고 ② 두 벌이 갈라진다.

→ **앱이 판정 결과를 내보낸다.** 앱이 뜰 때 앞으로 3개월분을 `window.isHoliday`로 계산해 `App_Config/DailyReport/_nonworkdays.json`에 쓴다(내용이 같으면 안 쓴다). 백엔드는 그 파일만 읽는다.

> **⚠️ 그 파일이 없거나 오래됐으면(예: 생성 30일 경과) 알림을 보내지 않는다.** 모르는 상태에서 보내면 설날에 "보고 쓰세요"가 간다. **모를 때는 안 보내는 쪽이 기본값**이다.

### 6-3. 휴가 판정 — 신뢰할 자동 출처가 **없다**

조사 결과:
- `insa_annual_plan_status()`는 **본인의** 연차계획서 작성 여부일 뿐 "누가 언제 쉬는지"가 아니다.
- 인사관리는 **각자 자기 계정으로 각자 PC에서** 로그인한다 → PM의 백엔드는 남의 근태를 못 읽는다.
- `insa_workplan_form`은 "브라우저에 그 신청서가 **열려 있을 때** 그 화면을 읽는 것"이다.
- 그룹웨어 `calendars()`는 로그인한 본인의 캘린더 목록 — **남의 휴가가 거기 보이는지 확인 못 했다**(§9-5).

→ **휴가를 일일보고의 한 종류로 만든다.** 모달에서 `일 종류: 휴가`를 고르면 그날 파일이 **생기고**(= 작성 완료) 알림 대상에서 빠진다. 하루치 입력이 클릭 2번이다. 미리 아는 휴가는 PM이 roster의 `leave`에 넣는다.

인사관리/그룹웨어 연동은 **3단계 이후**, 그리고 "남의 휴가가 실제로 보인다"를 **실측한 뒤에만.**

### 6-4. 보내면 안 되는 경우 (전부 **보내기 전에** 확인)

| 안 보내는 경우 | 근거 |
|---|---|
| 토·일 | `getDay()` |
| 공휴일·추가휴일 | `_nonworkdays.json` |
| `_nonworkdays.json`이 없거나 낡음 | **모르면 안 보낸다**(§6-2) |
| 그날 파일이 이미 있음 | list 1콜 |
| 종류가 휴가/반차/출장/교육 | 파일 내용 |
| roster `leave` 구간 | roster |
| `active:false` | roster |
| 마감시각 전 | `DAILY_POLICY.dueAt` |
| 오늘 이미 보냄 | 버킷 `daily:<날짜>:<사람>` |
| **NAS 조회가 실패했을 때** | ⚠️ 아래 |

> **⚠️⚠️ 조회 실패를 "미작성"으로 읽으면 전원에게 잘못 보낸다.** NAS list가 실패하면 "0건"이 아니라 **판단 불가**다. 이건 2026-11-03에 어댑터가 400을 ACL 거부로 보고 조용히 건너뛰어 목록이 빈 채 오류도 안 났던 것과 **같은 모양**이다. → list 실패 시 **전체 중단 + `_issueLog`**, 발송 0건.

발송 실패 시 버킷을 **올리지 않는다**(다음 틱에 재발송) — `_mail_watch_tick`의 *"발송 실패 시 lastId 안 올림"* 규칙 그대로.

### 6-5. 알림은 PM PC에서만 돈다

`telegram_config.json`은 PC 로컬이고 토큰이 있는 PC만 보낼 수 있다. 팀원 PC 백엔드도 전부 이 틱을 돌면 **중복 발송**이 된다. → `DAILY_POLICY.notifierKey`(roster에 적힌 계정 id 하나)와 **그 PC의 NAS 계정이 일치할 때만** 보낸다. 명단에 적힌 한 대만 울린다.

#### 7-1. js/59 구성 (데이터 먼저)

```
① 데이터(카탈로그) — 코드에 박지 않는 것
   DAILY_FIELDS      입력 칸 정의(key/label/labelEn/type/required)
   DAILY_DAY_TYPES   근무·휴가·반차·출장·교육 (+ 알림 면제 여부)
   DAILY_POLICY      dueAt / autoOpenModal / notifierKey / keepMonths / draftKey
   DAILY_PATHS       폴더·파일명 조립 규칙
② 저장소 — nasAppFile 위에 얇게. 쓰기는 통째, 읽기는 no-store.
   가드 2개: rev 충돌 / 빈 덮어쓰기 거부

④ 자동 초안 — globalData + changeLogs (AI 안 씀)
⑤ 입력 모달 — 모달 컨벤션 필수
```

## 8. 안 하는 게 나은 것 (과설계라고 보는 것)

1. **팀 하루 1파일 집계 원장** — §3-2. 오늘 사고 난 구조를 자발적으로 또 만드는 일이다.
2. **AI 자동 작성/요약** — 일일보고는 **짧게 쓰는 게 목적**이다. AI가 네 문장으로 부풀리면 아무도 안 읽고, 하루 한도를 먹어 메일 분석이 멈춘다. "일주일 요약"조차 2단계 이후, 그것도 사람이 누를 때만.
3. **결재·승인 워크플로** — 그룹웨어 전자결재가 이미 있다. 일일보고에 승인을 붙이면 **보고서가 문서가 되고 아무도 안 쓴다.**
4. **근태·출퇴근 시각 입력** — 인사관리(kInsa)가 이미 한다. 두 번 쓰게 만드는 전형이고, 맞춰야 할 책임만 생긴다.
5. **주간보고를 일일보고로 대체** — 축이 다르다(§1-1). 주간보고는 프로젝트별 PPT를 내야 한다.
6. **일일보고 엑셀 왕복(되돌려 넣기)** — §5-3. 남의 파일을 내가 쓰게 된다.
7. **업무 행마다 📔 버튼** — §4-3.
8. **읽기 권한 세분화** — NAS ACL은 팀 폴더 단위다. 못 하는 걸 할 수 있다고 하면 안 된다.
9. **"어제 안 쓴 것 소급 입력 금지" 같은 규칙** — 5명 팀에 규율 장치를 먼저 붙이면 도구가 감시로 읽힌다. 과거 날짜 수정은 그냥 허용.
10. **프로젝트별 일일보고** — 한 사람이 하루에 3개 프로젝트를 만지면 3건을 쓰게 된다. 1분이 3분이 되고 안 쓴다. **하루 1건에 업무를 여러 개 담는다.**

## 9. 사람에게 물어야 할 것 (추측으로 메우지 않았다)

### 9-1. ⚠️ 가장 중요 — **휴대폰에서 써야 하나?**

지금 저장소는 NAS 하나고, NAS는 **PC에서 도는 로컬 백엔드가 있어야** 닿는다. 앱이 모바일에 직접 그렇게 안내한다(js/57: *"📱 휴대폰·태블릿에서는 사내 NAS에 붙을 수 없습니다 — PC에서 열어주세요"*).

**일일보고는 퇴근길에 쓰고 싶어지는 종류의 기능이다.** 여기서 답이 갈린다.

- **PC만** → 위 설계 그대로. 1단계 반나절.
- **휴대폰도** → 설계가 **달라진다.** 브라우저가 NAS에 직접 못 붙으니 ① 사내 서버 상주 백엔드(장비·배포 문제) 또는 ② **텔레그램 봇으로 받기**(알림이 이미 텔레그램이고, 봇 답장을 백엔드가 `getUpdates`로 받아 적는다 — 단 그 백엔드가 켜져 있는 동안만).

②는 꽤 자연스럽지만 **설계 전제가 바뀌므로 지금 묻는다.**

### 9-2. 일일보고의 단위 — 하루 1건에 업무 여러 개(권장) vs 업무별 1건?
§8-10 근거로 전자를 권하지만, 지금 쓰고 있는 양식이 업무별이면 맞춰야 한다.

### 9-3. 열람 범위 — 전원이 전원을 보는가, PM만 보는가?
1단계는 전원 공개를 전제했다. NAS ACL로는 세분화가 안 된다(§5-4).

### 9-4. 마감 시각과 알림 시각 — 17:00? 18:00? 알림은 마감 30분 후? 다음날 아침?

### 9-5. 휴가 출처 — roster 수동 입력으로 시작해도 되나?
그룹웨어 캘린더에 **남의 휴가가 보이는지** 확인이 필요하다. 보인다면 3단계에서 붙일 수 있다(실측 먼저).

### 9-6. 계정 id ↔ 실명 매핑을 PM이 roster에 한 번 넣어도 되나?
5명이라 1회 5줄이다. `/telegram/members`에서 가져오기 버튼을 붙일 계획.

### 9-7. 주간보고는 유지인가?
유지 전제로 설계했다(§1). 폐지할 생각이면 주간보고 PPT를 일일보고에서 만들어야 하고, 그건 범위가 훨씬 크다.

### 9-8. 간트 "담당자" 칸이 실제로 채워져 있나?
**자동 초안 품질이 전부 여기 달렸다.** 비어 있으면 1단계는 "체크박스 목록" 대신 "빈 칸"이 되고, 사람이 다 타이핑해야 해서 1분 동선이 깨진다. → 착수 전에 프로젝트 2~3개의 담당자 칸 채움률을 **눈으로** 보는 게 좋다. (대안: 담당자 칸이 비면 **`changeLogs` 기반**으로만 초안을 만든다 — 이건 계정명이라 더 정확하다)

### 9-9. 과거 보고 보관 기간 — 무제한? 1년? 월 폴더 단위라 지우기는 쉽다.

### 9-10. 알림 수단 — 텔레그램만? 메일도?
메일 발송도 있지만, 미작성 알림을 메일로 보내면 받는 쪽이 더 무겁게 느낀다. 텔레그램만 권한다.
